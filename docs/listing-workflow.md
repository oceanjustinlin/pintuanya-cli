# 黑胶商品上架约束与验收

本规范记录 2026-10-24 用户确认的默认规则，配合项目 `AGENTS.md` 执行。当前状态：执行规则已确定；CLI 已有创建、图片上传、多规格、分类和分类内排序能力。`catalog-plan` 新建计划入口强制检查标题格式和显式规格；首页排序及库存后台语义仍待线上核实。

## 默认规则

| 项目 | 默认要求 | 验收依据 |
| --- | --- | --- |
| 图片 | 对应版本的黑胶示意图；新增规格时用本次第一个新增规格图片作商品主图及相册首图，保留历史图片和旧SKU封面 | 来源版本、CLI上传结果、商品cover、相册顺序及规格封面回查 |
| 标题 | `Artist - Title`，可靠发行日期可加在括号内 | 来源信息及商品标题回查 |
| 规格 | 单个版本也用 variants；`[独占渠道 - ]颜色 - 介质[ - 签名类型][ (/限量数)]` | 每个规格与来源逐一核对 |
| 库存 | 没说明就不设库存上限；不将发行限量当库存 | 请求映射及后台库存模式的实际证据 |
| 分类 | 新建、更新商品或更新规格后均移入目标拼团 NEW，已有商品不例外 | 分类查询、精确 UUID、写入后归属 |
| 排序 | NEW 内及店铺首页两处置顶 | 两个展示范围的实际顺序 |
| 先查重再分流 | Artist 和 Title 均匹配已有商品时，新增不同规格，复用原商品；相同规格不重复 | 全拼团扫描、候选身份核实、原商品及 SKU UUID |

示例标题：`Artist - Album (2026-11-20)`。示例规格：`Artist Store Exclusive - Opaque Red - 2LP - Signed Card (/1000)`。示例信息不代表真实发行资料。Signed Card 不改写为 Personally Signed；限量必须明确是对应版本的发行限量，不能将商店库存、编号样例或模糊营销文案当成限量证据。

## 执行清单

每次复制以下清单到 Git 忽略的 `plans/<任务名>-acceptance.md`，填写实际结果和证据；不得保存 Cookie、token 或其他登录信息。

- [ ] 来源：保存商品来源 URL、核对时间及版本依据；未知的可选日期、渠道、限量不填写。
- [ ] 输入：确认商品数、规格数、每个规格售价、颜色、介质、签名、图片与库存策略。缺价格、必要版本信息或可靠图片时暂停该商品。
- [ ] 预检：CLI 登录有效；目标拼团明确；NEW 唯一且 UUID 已核实；扫描全拼团商品，包括其他分组、未分组及下架商品。不能仅凭标题搜索无结果判定未创建。
- [ ] 查重分流：Artist 和 Title 分别匹配，核实疑似候选。唯一同一作品且规格不同则复用原商品追加；相同规格不重复添加；多个候选不自动选择。保存候选及分流依据。追加能力缺失时暂停写入，不能绕过检查另建商品。
- [ ] 图片：经 `upload-image` 上传，审核通过或已有文件回查可用；封面对应版本，不能只验证 URL 格式。新增规格时核对计划中新主图及相册首图均为本次首个新增规格图片，旧图片保留、旧SKU封面保持；执行后逐项回查。
- [ ] 计划：无已有同一作品时才用 `catalog-plan` 生成创建计划；人工按上述七条规则核对，只有一个规格也用 variants。复用原商品时应生成追加规格计划，保留原 UUID、SKU、价格、库存和销售设置；当前支持 append-variants 追加单维默认规格。
- [ ] 创建：用 `catalog-apply` 执行，保存状态；完整分类分页回查标题、图片、规格、价格、库存、分类和上架状态。
- [ ] 更新后迁移：新建、更新商品或更新规格回查通过后，若商品不在 NEW，单独生成 category 计划移入 NEW 并回查；不得以复用旧商品或保留原分类为由省略。
- [ ] NEW 置顶：迁移回查通过后，为商品 UUID 单独生成 sort TOP 计划并执行，CLI 回查 NEW 内位置。
- [ ] 首页置顶：依据已核实的首页机制通过 CLI 执行；如果与 NEW 共用排序，可复用同一次写入，但仍需独立验证首页。能力未实现时记录为未完成，不猜接口参数。
- [ ] 最终验收：再次核对 NEW 和首页位置，记录查询范围、时间、商品 UUID 与结果；首页需通过已核实的数据源用 CLI 回查；未经用户另行明确授权，不操作浏览器。
- [ ] 报告：逐项报告完成、失败和待验证状态。两处位置均核对通过后才报告流程完成。

批量创建时，新商品作为一组排在已有商品之前；批次内顺序在计划中明确，按 TOP 反向执行得到目标顺序。并发人工调整造成顺序变化时重新核对，不能无限自动争抢第一。

## 失败与恢复

| 故障 | 处理 |
| --- | --- |
| 分类缺失或同名多个 | 停止，不默认创建分类 |
| 创建超时、断网或回查不符 | 保留 sending 状态；原计划续跑只回查，禁止重复 POST |
| 创建已完成、排序失败 | 标记部分完成；使用已有商品 UUID 恢复排序，不重建商品 |
| 首页机制未知或 CLI 未支持 | 先只读调研，再补 CLI 和离线测试；未解决时不报告整体完成 |
| 回查发现商品内容已变化 | 停止，核对差异，不覆盖变化 |
| 图片审核拒绝或一直未完成 | 不使用该上传结果创建商品，回查后决定下一步 |
| 已存在同一作品 | 核实候选后用 append-variants；不支持的原规格结构停止并先补CLI，禁止新建替代 |

## 同一作品匹配的实现范围

新建计划使用 `category_goods(group, '')` 对全拼团的上架及下架商品完整分页，绕开后台标题搜索索引延迟。Artist 与 Title 分开比较：统一 Unicode、大小写及空白/标点表示，只移除 Title 末尾可识别的括号数字日期，保留 Deluxe、Remix 等其他内容。

两字段规范化后相同即阻止新建，提示核对原规格后追加；两字段各自的相似度均不低于 0.85 时视为疑似候选，必须核实。Artist 匹配且一个 Title 是另一个的完整词前缀时也列为疑似候选，用于召回旧标题带颜色或版本后缀的商品；例如 Album 与 Album (Red Vinyl) 或 Album (Deluxe Edition) 均需核实，不能自动认定版本可合并。相似度仅用于阻止可能重复的新建，不授权自动合并。无法解析的旧标题仍需按来源或其他查询词人工核实，不能声称算法覆盖所有旧命名。

同一计划中同一作品的不同规格必须合为一个 create 的 variants。新生成的 create 操作携带 `identity_check`，首次 apply 在 POST 前重新全量查重，防止计划生成后出现同一作品；创建进入 sending 后仍沿用只回查、不重复 POST 的恢复规则。旧计划不含该标记，执行前应重新生成。当前没有跨进程锁，回查和 POST 之间无法保证并发互斥。

已根据网页公开 transferGoods 与 updateGoods 调用链封装 append-variants：支持原有单维默认规格，或通过 existing_variant_name 明确命名旧单 SKU 后转换为规格，保留原SKU及商品设置，发送前校验完整快照；发送结果不确定时只回查、不自动重发。查重不会自动执行追加，仍须核对候选后生成追加计划。追加时复用原规格结构；旧规格结构不支持时先核实并补CLI；分类与 NEW 不同则在更新回查后另做 category 计划移入 NEW，再生成置顶计划。分类迁移不得改变原SKU价格、冻结、库存或销售设置，不擅自重新上架原本下架的商品。

## 测试与证据边界

运行全部离线回归：

```bash
python3 -m unittest discover -v
```

`test_listing_workflow.py` 验证关键流程：拒绝错误标题和隐式单 SKU、合规计划通过、单版本使用规格、默认及显式库存、图片必填、逐字段回查、分类缺失阻止计划、排序响应成功但位置不符时拒绝验收、排序中断后回查恢复。原有测试继续覆盖创建不确定时不重发、分页完整性、上传审核、凭据隔离及多规格。新增标题和规格校验先运行失败用例，再补实现；其余为已有行为的回归测试。

以下事项不能靠现有离线测试证明：

| 事项 | 所需验证 | 当前实现边界 |
| --- | --- | --- |
| 标题符合来源事实、图与版本一致、签名及限量准确 | 来源逐项核对 | CLI 不做事实识别 |
| 标题格式、必须使用 variants | 计划入口失败用例及合规计划用例 | 新建计划入口已强制；底层请求构造器及旧计划未追溯拦截，不能将其视为完整政策引擎 |
| 默认选择 NEW、规格语义完整 | 来源核对、分类查询及计划人工核对 | 尚未自动解析 NEW 名称及规格中的渠道、颜色、介质、签名和限量 |
| 已有同一作品的不同规格 | 查重与执行前复核已增加离线用例；追加动作另需协议验证、原 SKU 保留和幂等测试 | 已阻止新建替代；已支持单维默认规格追加，其他结构需先核实 |
| 不设置库存 | 通过命令行只读核对公开脚本协议和已有商品库存模式；必要时在下一件获准上架商品验证 | 省略 stock 目前编码成 0，离线测试只验证映射 |
| NEW 内置顶 | 线上 CLI 分类顺序回查 | 已有接口适配；离线排序测试不证明线上可用 |
| 店铺首页置顶 | 通过命令行只读核对顾客首页的数据源、筛选和排序及后台完整调用链；确认是否独立排序 | 尚未确认接口与现有分类排序的关系 |

所有来源核对、查询和复核均通过 CLI/命令行，不操作浏览器。线上验证先进行只读调研，不为测试擅自创建、编辑或删除真实商品。首次完整写入验证安排在下一件用户授权上架的实际商品；创建及排序均沿用 plan → apply，并保留回查证据。如需新增接口，先用脱敏协议样本补离线测试，再通过 CLI 实测。
